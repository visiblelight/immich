## 使用入口

- 后台相册 → 照片操作菜单 → “设为仅文章可见 / 恢复图库展示”。组卡片菜单可批量设置全组，组内成员菜单可逐张设置。保存是草稿；发布后在所有相册共享生效，仍保留后台成员关系。
- 后台文章 → 图片 → 单张图片 / 临时图片组 / 已有 Gallery 照片组。单张和临时组可从 Gallery 照片或上传素材选择。Gallery 选项包含来源相册已发布的隐藏作品；来源相册未发布时先在相册完成发布，隐藏作品不会因此出现在图库。
- 临时组明确选择该模式后，可跨相册及素材类型多选，拖动或箭头调整顺序，填写文章独立说明。重新编辑可增减与排序，至少两张。
- Gallery 照片组直接引用已有组，成员跟随来源组的发布更新；文章可以填写独立图注。临时组只跟随文章发布。
- 前台提供完整画面轮播、图片内浮动左右按钮、原生横向滚动/滑动和当前组内沉浸大图；无自动播放。文章素材继续不进入作品库。

## 2026-10-05 长文章发布耗时优化

用户反馈正式文章发布约 40 秒。生产入口日志确认发布成功，但旧日志没有请求耗时字段，不能精确还原当时各阶段耗时。使用该文章做只读复现（不再次发布、不修改生产代码或数据库）：展开后 77 次图片引用、75 张不同图片，读入两种展示图共约 109 MiB；引用查询约 468ms、文件读取约 513ms、图片处理约 35.1s，总计约 36.1s。主要开销是 `sanitizeImage` 每张执行 `sharp.stats()`，计算发布并不使用的像素统计；且串行校验期间一直持有站点写锁。不是 OSS 上传或 CDN 刷新等待。

本地实现：

- 使用完整图片输入的解码校验替代像素统计，丢弃校验用的单像素结果；实际输出仍直接保留 Immich JPEG/WebP 的压缩像素、尺寸与 ICC，仅移除隐私元数据，不生成或保存新的展示尺寸。拒绝解码警告，补充图片头正常但像素数据截断的回归检查。参照 [Sharp 输入接口](https://sharp.pixelplumbing.com/api-input/) 与 [构造参数](https://sharp.pixelplumbing.com/api-constructor/)。
- 每次发布按媒体类型及资源 ID 去重，最多两项并行；2048 项进程内内容哈希校验记录独立于 64 MiB 输出缓存，避免大文章淘汰缓存后重复解码。每次仍重新授权并读取文件；内容改变不会命中旧校验记录，记录不授予媒体访问权限。
- 解码校验在事务写锁外完成。提交时重新锁定并检查文章版本、全部引用的相册上下文和实时组成员；重新读取安全路径并比对每张展示图的 SHA-256。发生改稿、来源撤销、组成员变化或文件替换则拒绝发布，不产生部分 release。上传素材仍执行既有安全读取规则。
- 发布接口记录引用数、去重图片数、预检查／等待写锁／提交／总耗时及结果，不写入正文、标题、位置、凭据。编辑器显示发布阶段与已等待秒数，10 秒后解释仍在处理并提示避免重复点击；发布期间阻止重复提交及意外离开，失败恢复编辑。

在生产容器的独立只读诊断进程中加载候选图片校验实现（未替换运行服务）：相同 75 张图片首次校验约 5.5s，进程内再次校验约 0.9s，进程 RSS 约 354–368 MiB。这是图片校验阶段对比，不是完整发布请求延迟；生产整次发布尚待上线后验证。候选没有新增数据库迁移，也没有重新发布用户文章。
