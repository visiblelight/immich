# 开发、验收与常见排查

## 1. 每次工作的默认顺序

1. 读当前状态，查看 `git status`、分支和已有 diff；弄清本次需求及相关 ADR。先不修改无关文件。
2. 查实际实现和数据来源，区分设计样稿、本地真实数据、生产只读核验。用户说“本地先看看”不授权生产发布。
3. 小范围实现；公共组件尽量复用。数据结构有变化时同一功能更新迁移和数据字典，不改历史迁移。
4. 运行与改动匹配的检查；用真实本地样本验证，必要时合成数据覆盖失效与拒绝路径。不要为测试去改用户原片。
5. 说明具体变化、验证结果、仍存在的限制，给本地入口。涉及视觉调整等待用户验收；功能通过不等于视觉已接受。
6. 收到 commit/push/发布授权后，按[生产流程](production-operations.md)完成发布和验证；更新当前状态与交付记录。

用户重视数据保护、统一风格和真实闭环；不喜欢反复问已经授权的问题。合理的可逆实现继续推进，涉及新的生产范围、不可逆数据操作或缺失关键信息时再澄清。评论发信测试只能用获准地址，密钥/验证码不贴进聊天。

## 2. 检查命令与它们实际证明什么

在仓库根目录，使用锁定工具链：

```sh
sh deployment/gallery/scripts/pnpm.sh gallery:doctor
sh deployment/gallery/scripts/pnpm.sh gallery:check
sh deployment/gallery/scripts/pnpm.sh gallery:test
sh deployment/gallery/scripts/pnpm.sh gallery:build
sh deployment/gallery/scripts/pnpm.sh gallery:smoke
```

| 检查 | 能证明的范围 | 不能替代 |
|---|---|---|
| doctor | 基线与项目工具配置的检查 | 生产健康或完整业务验收 |
| check | TypeScript/Svelte 类型和组件检查 | 界面效果、真实数据库权限 |
| test | core/db 等已有单元测试 | 真正的 PostgreSQL 视图、HTTP 权限和图库行为 |
| build | 前后台及依赖能构建 | 已部署新版本 |
| smoke | 临时进程、路由和未配置环境的预期响应 | 真实图库 readiness；未配置 ready=503 是此测试预期 |
| test:db | 新建隔离 PG14 的结构、权限和合成业务回归 | 用户真实照片未被修改的哈希证据、视觉验收 |

纯文档变更检查引用、命令、路径和敏感信息即可，不必启动无关服务或全量重跑业务测试。已经通过的检查不无理由重复；修复测试发现的问题后重跑相应范围。

### 隔离数据库回归

先具备**当前 Immich 基线**的 `server/dist`、`packages/plugin-sdk/dist` 编译产物，再准备独立验证依赖。它不在主工作区运行 npm install：

```sh
sh deployment/gallery/scripts/pnpm.sh gallery:prepare:db-tests

sh deployment/gallery/scripts/pnpm.sh gallery:test:db \
  "$PWD/.gallery-local/immich-schema.sql" \
  "$PWD/.gallery-local/immich-migration-metadata.sql"
```

输入第一份必须是**schema-only** 导出，排除 Gallery，包含所需扩展；第二份仅包含 Immich migration_overrides/kysely_migrations 技术元数据。不要把完整私有业务 dump 传进去。安全导出方式见[数据库验证说明](../development/database.md)。测试创建隔离容器和合成用户/照片/发布数据，不向开发/生产库导入测试夹具。

专项可设置 `GALLERY_TEST_FOCUS=capture` 或 `community`；其他值执行 full。专项通过后，涉及跨模块公开资格、视图或角色变更仍需完整回归。缺少正确上游产物时先补齐，不伪造迁移记录或跳过漂移检查。

2026-11-01 的最近完整证据为 106 项单元测试、29 项隔离数据库测试通过，Immich 结构漂移为 0。这个计数不是未来测试必须保持的常量。

### 按改动选验收重点

| 改动 | 必要关注 |
|---|---|
| 普通样式/布局 | check/build，桌面与移动实测，长标题、无描述、零评论等状态 |
| 公共媒体/发布资格 | 当前 release、祖先下线、来源停用、资产删除、路径逃逸、文章单独公开；DB 完整回归 |
| GPS/时间 | 有/无 offset、有效/失效 GPS UTC、缺定位、历史时区、只改位置复用、原始时间改变不复活、停用、排队失败与刷新 |
| 到访 | 自动/人工成员、合并拆分、国家和省级排序、补照片不改人工成员、前台日期 |
| 评论/用户 | 邮箱唯一/名称不唯一、未注册登录、开关组合、审核、只显示公开目标、改绑/退出撤销、纯文本 |
| 文章保存 | 长文章、表格工具栏、响应式数据序列化、失败提示可见、草稿不丢、图片组/封面直链 |
| OSS/作者信息 | 下载实际输出读取元数据、像素/色彩保持、幂等同步、撤销与缓存、业务 ID 不变、Immich 文件哈希不变 |
| 迁移/升级 | 隔离恢复、角色最小权限、迁移校验和、数据计数/哈希、Immich 漂移、可执行回退范围 |

## 3. 常见问题的排查入口

| 现象 | 先查什么 | 不要怎么做 |
|---|---|---|
| 页面 503/空库 | 环境是否加载、runtime 角色、schema 契约、站点初始化与 source scope | 不盲目再次 local:init，不给 runtime owner |
| 本地容器 Up，Immich API 不通 | 2283 实际响应、Redis、server 日志、Linux 依赖卷与宿主安装记录 | 不以删除数据库/卷解决 ExifTool 或 native module 错误 |
| 补 GPS 后仍待核对 | 源签名、是否排队、worker 是否运行、读取失败、是否有时间基线；核对真实状态而非旧截图 | 不因为 city 名称存在就断言相机时区已知 |
| 当前与预览钟表一样，却提示 UTC 变化 | 检查地点时区是否未知、显示的是相机时间还是地点时间；分开展示瞬间变化与墙上钟表 | 不直接用服务器时区格式化，也不隐瞒缺失信息 |
| 某照片无前台链接 | 是否相册公开、文章单独公开、仅后台可见；查询汇总路径 | 不为方便核验绕过授权开放 asset ID |
| 相同国家出现多段行程 | 自动段与人工段、成员和日期跨度、新补照片 | 不自动吞并人工行程 |
| 长列表查询超时 | SQL 与视图重复扫描、N+1、排序/分页前后次序 | 不先扩大 statement timeout 或权限来掩盖 |
| 邮件未收到 | DirectMail 凭据/发信域名、允许注册、用户是否存在、发送结果、冷却时间 | 不记录验证码、使用固定万能码或扩大 RAM 权限 |
| 文章无法保存 | 真实错误、结构验证、响应式对象 clone、网络/Origin、草稿保留 | 不 catch 后假报成功或清空正文 |
| CDN 图片未变/仍可下载 | 内容版本、同步状态/允许清单新鲜度、短时签名到期、当前公开资格 | 不清空所有 OSS 文件或公开整个 Bucket |

上次已修复的大图库超时来自逐张扫描公开链接资格视图；现为一次汇总匹配。未来新增照片后台字段时警惕重新引入 N+1。文案状态要区分“后台正在处理”“缺地点”“缺源时间证据”“证据冲突”，不能一概叫待人工核对。

## 4. 提交与文档维护约定

- 提交中文标题，正文详细写目的/问题、主要变化、验证、兼容和回退。不要只有一句标题，不自动提交用户已有改动。
- 本轮文档也修改了 `deployment/gallery/cloud/README.md`，该路径匹配 Gallery workflow；用户已授权交接文档和本地升级配置分别提交、推送，两个提交均使用 `[skip ci]`，不触发生产发布。只看扩展名为 `.md` 不能推断不会触发 CI。
- 需求确认写 ADR；结构说明写 architecture；实际本地/生产验收写 delivery。分别注明时间和环境，保留旧阶段证据。
- 发布后更新 handoff/current-state 的应用 SHA、镜像/迁移范围和交付链接。测试数量、照片数量是带日期的样本，不写成产品规则。
- 新路径、端口、凭据用途、定时任务变更，同步 local-and-transfer / production-operations。
- 不把真实私有照片、完整业务导出、OTP、邮箱清单、密钥或 cookie 写入文档。截图/日志留在受保护忽略目录；公开文档只写必要的非敏感结论。
- 专项历史脚本可能含当时的数据库/资产/提交假设。将可复用逻辑放进受版本管理的脚本；不要让下个 agent 必须找到旧聊天工具调用才能部署。

本次交接文档自身的整理与验证记录见[文档交付记录](../delivery/agent-handoff.md)。
